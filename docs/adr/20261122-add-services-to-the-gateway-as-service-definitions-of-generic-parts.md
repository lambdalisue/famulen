# サービスはつなぎ方を書いたデータ（サービス定義）でゲートウェイに足し、ゲートウェイは一般の部品だけを持つ

状態：採用

## 背景

ゲートウェイがつなぐサービスには、MCP サーバーや HTTP API のほかに、Google や Slack のように、自分で登録したアプリでのログインや、届いたものを受ける口が要るものがある。ただ、そのつなぎ方は、OAuth 2.0 でトークンを得る、HTTP の API を呼ぶ、決まった手順で届いたものを受ける、という一般の部品の組み合わせでできている。サービスの名前で分かれる処理をゲートウェイの中に書くと、サービスが増えるたびにゲートウェイの中が分かれていく。

## 決定

ゲートウェイは、通り道（MCP・HTTP API・コマンド）、ログインの仕方（なし・鍵・登録したアプリでの OAuth 2.0・MCP の認可の手順）、受け口（HTTP の受け口と届いたものの確かめ方、Socket Mode・Pub/Sub の pull・コマンドの出力のようなゲートウェイから張る接続の手順）という一般の部品だけを持つ。サービスは、これらの組み合わせをデータとして書いたサービス定義で足し、ゲートウェイはサービスを名前で知らない。サービス定義には事実だけを書き、ロジックは書かない。

## 検討した他の案

- サービスの種類ごとに差し込み口を実装して足す。Google や Slack の固有の扱いは種類の中に閉じるが、新しいサービスのたびにコードが要り、一般の手順が種類ごとに書き直される。
- MCP と HTTP API を汎用に扱い、Google と Slack はゲートウェイの中に個別に書く。サービスが増えるたびにゲートウェイの中の分岐が増える。

## 結果

- 新しいサービスは、サービス定義を 1 つ書けばつなげる。Google と Slack は、ゲートウェイが同梱するサービス定義になる。同梱するのはデータだけで、ゲートウェイのコードはサービスを名指さない。
- データで書けない接続の手順と、届いたものの確かめ方（署名）は、サービスではなく手順の名前で、一般の部品として持つ。
- 権限・金庫・控え・呼び出しの流れは、どのサービス定義にも同じように効く。
